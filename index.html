01 · FULL STACK MONOREPO

Standard MES

수주 · 자재 · 생산 · 품질 · 설비 · 출하까지 제조 실행 전 과정을 다루는 표준 MES입니다. 특정 회사에 종속되지 않도록 도메인을 일반화했습니다.

개인 프로젝트 · 도메인 설계, DB 스키마, 백엔드, 프론트엔드 4종까지 전체 구현

24도메인
61테이블
4+1프론트 + 백엔드

풀려던 문제

제조 현장에서 사무직, 작업자, 태블릿 사용자, 관리자는 같은 데이터를 보지만 필요한 화면과 조작이 전혀 다릅니다. 하나의 화면으로 모두를 만족시키려다 어느 쪽에도 맞지 않는 UI가 되는 문제를 해결하려 했습니다.

설계 선택

  • 단일 백엔드 · 다중 프론트엔드 — Spring Boot 백엔드 하나를 4개 프론트가 공유합니다. 데이터와 권한 규칙은 한 곳에서 관리하고, 사용 환경별로 UX만 분리했습니다.
  • 횡단 관심사 단일화 — 응답 포맷, 예외 처리, 에러 코드, 페이징 계약을 각각 한 곳에 모았습니다. 한 곳만 고치면 24개 도메인 전체에 전파됩니다.
  • 도메인 값의 데이터화 — 상태·구분 값을 코드에 하드코딩하지 않고 공통코드 마스터로 관리해, 업종이 달라져도 코드 수정 없이 대응합니다.
  • 운영 고려 — 작업지시 목록 같은 핫 리드는 Caffeine·Redis로 캐싱하고, 생산 이력은 LOT 단위로 추적 가능하게 채번합니다.

라이브 데모(사무/관리 화면)는 로그인 화면부터 시작합니다. 데모 계정 mesadmin / ChangeMe!2026 으로 접속해 보세요.

설치와 실행 방법, 상세 문서는 저장소 README에 정리돼 있습니다.

Dayflow

필요한 기능만 켜서 쓰는 모듈형 일정 관리 웹앱입니다. 학부 팀 프로젝트를 현재의 기술로 다시 만든 개인 리메이크입니다.

개인 프로젝트 · 기획, 백엔드, 프론트엔드 전체 구현

3사용 모드
PWA설치형
오프라인쓰기 지원

풀려던 문제

일정 관리 앱은 기능이 많을수록 좋아 보이지만, 실제로는 학생·직장인·미니멀 사용자가 쓰는 기능이 서로 거의 겹치지 않습니다. 모두에게 같은 화면을 강요하면 누구에게나 복잡한 앱이 됩니다.

설계 선택

  • 기능 모듈 토글 — 학생 · 직장인 · 미니멀 모드로 기능 묶음을 켜고 끕니다. 안 쓰는 기능은 화면에서 아예 사라집니다.
  • 상황에 맞는 알림 경로 — 앱을 보고 있을 땐 SSE 실시간 토스트, 앱이 꺼져 있을 땐 Web Push로 갈라 처리했습니다.
  • 오프라인 우선 — 연결이 끊겨도 읽기·생성·수정·삭제가 되고, 재연결 시 자동으로 동기화합니다.
  • 가벼운 백엔드 — PocketBase 단일 실행 파일을 써서 계정 발급이나 클라우드 설정 없이 누구나 로컬에서 바로 띄울 수 있게 했습니다.

03 · FULL STACK

Standard CMS

영업·상담 조직을 위한 고객 관리 시스템입니다. 고객 정보, 상담 이력, 계약, 담당자를 한 화면 흐름 안에서 관리합니다.

개인 프로젝트 · 기획, 백엔드, 프론트엔드 전체 구현

풀려던 문제

고객 관리 화면은 목록 · 검색 · 필터 · 상세가 계속 반복되는데, 화면마다 따로 만들면 조작 방식이 조금씩 달라져 사용자가 매번 다시 배워야 합니다.

설계 선택

  • 목록 경험의 통일 — 고객·상담·계약 목록이 같은 검색·필터·페이징 규칙을 공유하도록 공통 훅으로 묶었습니다.
  • 대시보드로 맥락 제공 — 6개월 추이와 지역별 분포를 recharts로 시각화해, 목록에 들어가기 전에 전체 상황을 먼저 보게 했습니다.
  • 빠른 등록 — 전체 폼을 열지 않고도 최소 항목만으로 즉시 등록할 수 있는 경로를 따로 뒀습니다.
  • 접근성 있는 기본 요소 — 모달·드롭다운 등은 Radix UI를 써서 키보드 조작과 포커스 관리를 직접 구현하지 않았습니다.

설치와 실행 방법, 상세 문서는 저장소 README에 정리돼 있습니다.

01 · HOW I BUILD

문제와 사용자부터 정의

기술 선택보다 먼저 누가, 어떤 상황에서, 왜 쓰는지를 정리합니다. 같은 기능이라도 사용자가 다르면 다른 화면이 맞다고 봅니다.

실제 적용

  • Standard MES — 사무직·현장 작업자·태블릿 사용자·관리자가 같은 데이터를 보지만 필요한 화면이 전혀 달라, 백엔드 1개에 프론트엔드 4개로 나눴습니다.
  • Dayflow — 학생·직장인·미니멀 사용자가 쓰는 기능이 거의 겹치지 않아, 기능을 모듈로 쪼개 필요한 것만 켜서 쓰도록 설계했습니다.
  • Standard CMS — 목록·검색·필터·상세를 반복해서 쓰는 영업·상담 조직 사용자가 화면마다 다른 조작 방식을 다시 배우지 않도록, 문제를 "목록 경험을 일관되게 만드는 것"으로 좁혀서 정의했습니다.

02 · HOW I BUILD

작게 실행하고 확인

기능을 한 번에 완성됐다고 가정하지 않습니다. 작은 단위로 쪼개서 만들고, 만들 때마다 실제로 실행해서 확인한 뒤에만 다음 단계로 넘어갑니다.

이렇게 합니다

  • 화면이든 로직이든 전체를 다 만들어두고 나중에 몰아서 점검하지 않습니다. 작은 조각이 끝나는 대로 그 자리에서 바로 확인합니다.
  • 확인되지 않은 부분 위에 다음 작업을 쌓지 않습니다. 앞이 불확실하면 거기서 멈추고 원인부터 찾습니다.
  • 눈으로 봐서 판단이 안 서는 문제는 추측으로 고치지 않고, 직접 실행한 결과나 측정값으로 원인을 확인한 뒤에 고칩니다.

03 · HOW I BUILD

공통 구조로 복잡도 관리

반복되는 UI와 로직은 공통 구조로 모으고, 기능의 책임이 한 곳에 섞이지 않도록 나눕니다.

실제 적용

  • Standard MES — 응답 포맷, 예외 처리, 에러 코드, 페이징 계약을 각각 한 곳에 모아, 한 곳만 고치면 24개 도메인 전체에 전파되도록 했습니다.
  • Standard CMS — 고객·상담·계약 목록이 검색·필터·페이징 규칙을 공통 훅 하나로 공유하도록 묶었습니다.
  • Automation Suite — 브랜치 생성·코드 리뷰·테스트·최적화로 흩어지기 쉬운 반복 작업을 개발 콘솔 하나로 묶었습니다.

04 · HOW I BUILD

확인한 것만 공개

AI가 생성한 코드를 그대로 믿지 않습니다. 기능이 여러 단계로 이어지는 흐름이면 첫 단계부터 끝 단계까지 순서대로 직접 실행해 보고, 끊김 없이 돌아가는 것만 적용합니다.

이렇게 합니다

  • AI가 만든 코드라고 검증을 건너뛰지 않습니다. 사람이 짠 코드와 같은 기준으로 실행해서 확인합니다.
  • 여러 단계가 순서대로 이어지는 기능은 중간을 건너뛰지 않고, 처음부터 끝까지 차례로 직접 실행해 흐름 전체가 끊기지 않는지 확인합니다.
  • 확인되지 않은 부분이 남아 있으면 적용하지 않고, 문서로 현재 기능 상태를 관리합니다.
